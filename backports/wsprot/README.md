# Защита файлового кэша (идея le9, написано под это дерево)

Проблема: на 2-3 ГБ RAM при нехватке памяти ядро вытесняет горячий файловый кэш (код приложений, библиотеки), потом читает его с eMMC обратно: UI залипает, при этом anon-память можно было бы дёшево выгрузить в zram.

Что делает: sysctl `vm.file_protect_kbytes` (по умолчанию 0 = выключено, поведение как без патча). Если он ненулевой и в зоне файловых страниц (active+inactive) не больше порога, глобальный reclaim выбирает `SCAN_ANON`. Условия: `swappiness > 0`, есть своп (проверка наличия свопа в `get_scan_count` идёт раньше), приоритет reclaim не ниже 3 (под сильным давлением защита снимается, чтобы не довести до OOM). Только глобальный reclaim.

Важно: встроенный LMK (`lowmemorykiller`) считает «свободный файловый кэш». Если порог выше самого большого `minfree`, LMK может перестать срабатывать, пока кэш защищён. Держите порог ниже, например 100-200 МБ при `minfree` до 300 МБ, и проверяйте `memlog`.

Включение: `experiments=wsprot` (порог 0, задавать руками: `echo 204800 > /proc/sys/vm/file_protect_kbytes`) или `wsprot200` (группа `vm` пишет 200 МБ).

Файлы: `include/linux/swap.h`, `kernel/sysctl.c`, `mm/vmscan.c`. Проверено: накладывается, компилируется. Не проверено: на устройстве; это самый рискованный из трёх, потому что меняет reclaim. Если после включения растёт число убийств приложений или `kswapd` держит CPU, верните 0.

## Результат на телефоне (Redmi 8)
Тест `mem` при swappiness 150, порог 100 МБ против 0 (3 раунда на значение): оба варианта удержали 33 из 33; прямой reclaim 96,1 тыс. против 105,1 тыс. страниц (в пределах разброса); тёплый запуск 363 против 350 мс; refault и major fault во втором проходе не снизились. Вывод: пользы не показал, риск больше, в сборку не включать.
