# lzo-rle для zram (бэкпорт из Linux 5.1)

Что делает: добавляет алгоритм сжатия `lzo-rle` (LZO с кодированием длинных серий одинаковых байтов; на страницах, забитых нулями и повторами, быстрее обычного `lzo`).
Появляется в `/sys/block/zram0/comp_algorithm`. По умолчанию его делает `zram_comp=lzo-rle` (бэкпорт включается сам); иначе только доступен для ручного выбора.

Что внутри (`lzorle.patch`, 7 файлов):
- `lib/lzo/lzo1x_compress.c`, `lzo1x_decompress_safe.c`, `lzodefs.h` и `include/linux/lzo.h`: из Linux v5.4 как есть.
  В закреплённом коммите все четыре файла были побайтно равны v4.9, поэтому замена чистая. Побочный эффект: обычный `lzo` тоже получает ускорения 5.x для arm64 (CTZ64, копирование по 8 байт).
- `crypto/lzo-rle.c`: новый файл, обёртка в стиле `crypto/lzo.c` ядра 4.9 (в 5.4 она написана под scomp, которого в 4.9 нет). `crypto/Makefile`: собирается вместе с `lzo.o`.
- `drivers/block/zram/zcomp.c`: строка `"lzo-rle"` в списке алгоритмов.

Включение: `experiments=lzorle` (шаг workflow применяет патч через `scripts/apply_backports.py`, `apply_tweaks.py` включает `CONFIG_CRYPTO_LZO=y` и проверяет, что патч наложен).

Проверено:
- патч чисто ложится на файлы закреплённого коммита;
- компилируются `lib/lzo`, `crypto`, `drivers/block/zram`, `fs/pstore`, `lib/decompress_unlzo.c` clang-16 с флагами сборки;
- круговой тест (6000 буферов от 1 байта до 64 КБ: случайные, нули, длинные серии, смесь; сжатие `lzorle1x_1_compress` и `lzo1x_1_compress`, распаковка `lzo1x_decompress_safe`) на x86-64 и на aarch64 под qemu с `CONFIG_ARM64` и эффективными unaligned: расхождений нет.

Тест лежит в `test/` (`KERNEL=/путь/к/ядру ./run.sh`, после наложения патча).

Не проверено: на железе. Выигрыш в скорости не измерен: сравнивайте `kknx-test.sh zram` (в тест уже добавлен `lzo-rle`).
Данные zram живут только в ОЗУ, поэтому смена алгоритма между сборками ничего не ломает.
